= NAV ident komponent

Heretter "NIK"

== Hvorfor trengs denne komponenten?

Må kunne generere nav-identer unikt, og uten konflikter. Da må det være en sentral komponent som står for dette.

Generering og bokholderi på nav-identer blir en veldig stabil type funksjonalitet som ikke vil endre seg særlig over tid.

Kan gi ifra oss NIK til f.eks IDM på sikt om dette er mer hensiktsmessig

Ved å trekke ut nav-identer i egen komponent, vil vi slippe at NOM må håndtere corner-caser som
vikafossen, roboter og utenlandskonsulenter

=== REST

Bestilling blir på rest.
En bestilling vil gi en ny eller eksisterende navident tilbake basert på om personidenten finnes ifra før.
Bestilligen må angi når denne navidenten skal være aktiv fra dato.
Bestillingen vil knyttes til pålogget nav-ident via aad-obo

==== Opprette eller reaktivere en navident

request:    POST /personid
```
{
    personid: string påkrevd (f-nr, d-nr, annen nøkkel)
    identType: string <ROBOT | ORDINÆR | UTENLANDSK_KONSULENT> - Default MENNESKE
    aktivFra: date - Default - dagens dato
}
```

respons:
```
200 OK          hvis den eksisterer ifra før
201 CREATED     hvis den blir nyopprettet
body:
{
    navident: <ny eller eksisterende navident for angitt personid>
    aktivFra: Datoen fra requesten
}

409 CONFLICT    Hvis den allerede er aktiv
body:
{
    navident: <navident for angitt personid>
    aktivFra: Datoen den er aktiv fra ifra før
    feilmelding: "Navident for angitt personid er allerede aktiv"
}

409 CONFLICT    Hvis requestens aktivFra er før evt seneste periode sin aktivtil dato (kan ikke ha overlappende periode.
body:
{
    navident: <navident for angitt personid>
    aktivFra: Start datoen for seneste aktive periode
    aktivTil: Slutt datoen for seneste aktive periode
    feilmelding: "Navident for angitt personid kan ikke settes aktiv fra angitt dato siden dette er i en allerede deaktivert periode"
}

404 NOT FOUND       Angitt personid for ordinær ident finnes ikke i PDL
body:
{
    feilmelding: "Angitt personid for ordinær ident finnes ikke i PDL"
}

500 Internal Server Error
body:
{
    feilmelding: <Feilårsak>
}
```

REST tjenesten utfører følgende handlinger:
- Lager AKTIVER event på kafka (egen request/forespørsel topic?) som en 'need' melding
```
    {
        personid: string påkrevd (f-nr, d-nr, annen nøkkel)
        identType: string <ROBOT | ORDINÆR | UTENLANDSK_KONSULENT>
        aktivFra: date
    }
```
- 'Query' - konsument slår opp om det finnes eksisterende navident og legger til dette i 'need' medlingen over
```
    {
        ...<tidligere data i need melding>...
        eksisterendeIdent: { <Tom hvis den ikke eksisterer>
            navident: <eksisterende navident>
            aktivFra: fra dato for sist gjeldende periode
            aktivTil: eventuell til dato for sist gjeldende periode
        }
    }
```
- 'PDL' - konsument sjekker mot PDL for å finne personident hvis identtypen er ORDINÆR.
Populerer eksisterende informasjon om personid i 'need' meldingen over
```
    {
        ...<tidligere data i need melding>...
        pdl: {
            personid: <string (fnr/d-nr)> - den gjeldende id'en i PDL
            allePersonider: [ <Tom hvis den ikke eksisterer i PDL>
                personid: <string (fnr/d-nr)>
            ]
        }
    }
```
- 'NAV ident generator' - konsument trår til hvis need meldingen har fått feltet 'eksisterendeIdent' men den er tom. Da lager den ny ident og legger det til i need meldingen:
```
    {
        ...<tidligere data i need melding>...
        nyNavident: <Ny generert navident>
    }
```
- 'Respons' konsument kan returnere svar så fort den enten har funnet en eksisterende ident. Eller need meldingen har fått 'ny navident' og PDL ident finnes hvis det er ORDINÆR ident. Respons konsumenten kan legge til sin fulle respons til i 'need' meldingen.
```
    {
        ...<tidligere data i need melding>...
        respons: {
            responseCode: <HTTP response code>
            responsBody: {
                <Som returert i REST meldingen>
            }
        }
    }
```
- 'Respons' - konsumenten må også lage en event melding på eventsource køen, og også persistere denne i base. Event hendelsen vil være enten en 'OPPRETT' eller en 'REAKTIVER' melding.

=== Hypoteser

- Roboter, utenlandskonsulenter, og vikafossen identer skal ikke inn i NOM
- utenlandskonsulenter trenger ikke være i lønnssystemet for å få betalt
- Kun eksternt/statlig/kommunalt ansatte skal inn i NOM
- Testpersoner skal ikke inn i NOM
- Roboten skal vite om sin org-tilknytning, men NOM vet ikke om roboten
- lønnsnr er likt navident uten prefix bokstav
- (?) Roboter har fast prefix-bokstav i sin nav-ident
- vikafossen har prefix-bokstav "s", av fiktivt etteravn "Skjult"
- egentlig 3 stykker fiktiv/skjult/ukjent etc
- anonyme nav-identer har prefix-bokstav "a", av fiktivt etternavn "Anonym"
- Verifisering av identitet:
- identiteten er verifisert FØR den når NIK
- (?) NIK skal ikke inneholde navn
- Navn berikes andre steder, eller er ikke nødvendig
- NIK må inneholde navn der PDL ikke kan bidra med navn
- Det skal opprettes "ROBOT-NOM" av et annet team som holder styr på idente rsom ikke skal i NOM!
- IDM holder styr på tilgangene til roboten, NIK holder styr på identen til roboten. Hvis mer info om roboten behøves, f.eks navn: så vet vi ikke.
- NIK er slave av NOM (eller andre) når det kommer til navn
- Kan ikke endre en bestilling tilbake i tid for audit-formål
- NIK stoler på at bestillingene den får er verifisert av bestiller (f.eks nom/remedy) mtp gyldig personident
- IDA-identer starter alltid med Z som bokstav-prefix
